01 · Anatomy of a request

One request, two very different phases.

An LLM answers in two phases. Prefill reads the whole prompt in one parallel pass and fills the KV cache. Decode then generates the answer one token at a time, because each token depends on the previous one. The two phases stress the GPU in opposite ways.

Illustrative rates: prefill ≈ 12,000 tok/s, decode ≈ 55 tok/s for one stream on one modern GPU.

Why the split matters. Prefill is compute-bound: thousands of tokens multiply through the weights at once. Decode is memory-bandwidth-bound: for every single token, the GPU must stream all the weights and the KV cache from memory. One phase saturates FLOPs, the other saturates HBM. Keep this asymmetry in mind — the whole tutorial builds on it.

Requests are also wildly heterogeneous. A RAG query reads 20,000 tokens and writes 100. A reasoning agent reads 500 and writes 4,000. A "fix this typo" completion does neither. Classic web load balancing assumes short, uniform requests — LLM traffic breaks that assumption, which is where this tutorial ends up. First: where does all the memory go?

02 · The KV cache

The thing that actually eats your GPU.

Attention lets each new token look at every previous token. To avoid recomputing the past on every step, the engine caches each token's attention keys and values — the KV cache. It grows linearly with context length and with the number of concurrent requests, and it must live in GPU memory next to the weights.

KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes_per_value

Two takeaways. First: batch size — and therefore throughput — is capped by KV-cache memory, not by compute. Second: a 70B model at FP16 does not fit on any single GPU, so multi-GPU serving is not an optimization — it is the entry ticket. Both problems come up next.
03 · vLLM

Continuous batching and PagedAttention.

vLLM is the de-facto open-source serving engine, and it rests on two ideas. Continuous batching admits and retires requests at every decode step instead of waiting for a whole batch to finish. PagedAttention stores the KV cache in small fixed-size blocks, like virtual memory pages, instead of one contiguous slab per request.

PagedAttention: KV cache without fragmentation

Early engines reserved one contiguous memory region per request, sized for the maximum possible context. Most of that reservation sat empty. vLLM instead slices the cache into blocks (16 tokens each in vLLM's default configuration) and keeps a per-request block table — so blocks land anywhere, nothing is reserved up front, and two requests can even point at the same block when they share a prefix.

Result: near-zero waste means more concurrent sequences fit in the same memory, which directly raises throughput — remember, batch size is memory-capped. The paper is "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP 2023).
04 · Prefix caching

Most prompts repeat. Stop recomputing them.

Blocks are content-addressed: hash the tokens, and identical prefixes map to identical blocks. vLLM's automatic prefix caching exploits this. A chat sends the whole conversation back on every turn; an agent re-sends its system prompt and tool definitions hundreds of times. If the blocks are still resident, prefill skips them entirely — and TTFT collapses.

05 · Across GPUs

Four ways to split a model.

When one GPU is not enough, you must choose what to split: each weight matrix (tensor parallelism), the layer stack (pipeline parallelism), the request stream (data parallelism), or — for mixture-of-experts models — the experts themselves (expert parallelism). Each choice buys a different thing and pays a different communication bill.

StrategyWhat is splitvLLM flagUse whenCommunication cost
Tensor (TP) Every weight matrix, column/row-wise (Megatron-style) --tensor-parallel-size Model too large for one GPU but fits on one node All-reduce every layer — needs NVLink-class bandwidth
Pipeline (PP) The layer stack, into sequential stages (uneven splits allowed) --pipeline-parallel-size Across nodes, or GPUs without NVLink (e.g. L40S) Activations once per stage boundary — cheap, but adds latency
Data (DP) Nothing — full replicas, independent KV caches --data-parallel-size Model fits; you need throughput None between replicas — but now you need a smart router
Expert (EP) MoE expert layers, spread across GPUs --enable-expert-parallel Sparse MoE models (DeepSeek-class), usually DP attention + EP experts All-to-all token dispatch at every MoE layer

The vLLM docs' rule of thumb is short enough to memorize:

# fits on one GPU?            → no distribution needed
# fits on one node?           → TP = number of GPUs on the node
vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4

# needs multiple nodes?       → TP = GPUs per node, PP = number of nodes
vllm serve big-model --tensor-parallel-size 8 --pipeline-parallel-size 2  # 16 GPUs

# MoE throughput at scale     → DP for attention + EP for experts
vllm serve deepseek-model --data-parallel-size 4 --enable-expert-parallel
Multi-node footnote. vLLM uses Ray by default for multi-node serving (--distributed-executor-backend ray) and Python multiprocessing within a node. Cross-node TP is only viable on RDMA-class networks — if NCCL logs say [send] via NET/Socket, your interconnect is the bottleneck, and PP across nodes is the better trade.
06 · The load balancing problem

Round-robin meets a prefix cache. It loses.

Scale-out means data parallelism: N replicas behind a router. Kubernetes gives you round-robin for free, and for stateless microservices it is fine. LLM replicas are not stateless: each one carries queues of wildly different cost and a KV cache full of someone's conversation. A router that ignores both recomputes prefixes constantly and parks cheap requests behind 25,000-token monsters.

Simulator: one workload, three routing policies

4 replicas. 20 multi-turn agent sessions (growing 4k–12k-token prefixes) plus 3 one-off 12k–20k token RAG requests. Each replica prefills one request at a time and keeps an LRU prefix cache (100k tokens). The prefix-aware policy scores 2.0 × prefix-match + 1.0 × (1 − load) — the same weighted-sum shape llm-d uses.

Note the trap: least-loaded can lose even to round-robin, because it counts requests, not tokens — a replica mid-way through a 20k-token prefill looks idle and attracts work. Load signals must be token-aware (llm-d ships a token-load-scorer for exactly this).

This is not a toy effect. In the llm-d community's May 2025 benchmark (LLaMA 4 Scout FP8, two 8×H100 nodes, long-input multi-turn QA), prefix-aware routing delivered a mean TTFT about 3× lower than the baseline load balancer at 4 QPS, and sustained ~50% to 2× more QPS within a P95 TTFT SLO. Google reports that its Gemini-serving platform doubled its prefix-cache hit rate from 35% to 70% with the same routing family (vendor-reported, October 2026). Sources in the footer.
07 · llm-d

Kubernetes-native brains for the router.

llm-d is a CNCF Sandbox project (announced May 2025 by Red Hat, Google, IBM and others; v1.0 shipped October 2026) that packages exactly this routing intelligence for Kubernetes. It does not replace vLLM — it orchestrates a fleet of vLLM (or SGLang, or TensorRT-LLM) pods and decides, per request, which pod wins.

The llm-d Router = any Gateway-API proxy (Istio, Envoy AI Gateway, GKE Gateway…) + the Endpoint Picker, attached via an InferencePool CRD and Envoy's ext-proc protocol (Gateway API Inference Extension).

The scheduler: Filter → Score → Pick

For each request, the Endpoint Picker (EPP) filters candidate pods (by role, label, SLO tier), lets every enabled scorer grade each pod from 0.0 to 1.0, multiplies each score by its configured weight, sums, and the max-score-picker takes the winner. The scorers shipped in v1.0 include:

How does the router know what each pod has cached?

Two modes, one trade-off:

  • Precise — vLLM pods publish BlockStored / BlockRemoved / AllBlocksCleared KV-events over ZMQ; the EPP's KV-cache indexer keeps a live block-key → pods map. Exact, at the cost of an event pipeline.
  • Approximate (the default) — no events at all. The EPP hashes the prompt into 64-token blocks and remembers, in a local LRU, which pod it recently sent each prefix to — assuming that pod still holds it. Cheap, but it can drift from reality after cache eviction.
Adoption path (from the 1.0 announcement): start by putting prefix-aware routing in front of the vLLM deployment you already have. Add flow control, KV-cache offloading (host RAM → SSD), and disaggregation only when the workload asks for them. Which brings us to the flagship feature…
08 · Prefill/decode disaggregation

Split the two phases onto different pods.

Section 01 showed that prefill is compute-bound and decode is memory-bound. On a shared replica they fight: one long prefill stalls every decoding stream on the pod (the ITL spikes you see in production). Disaggregation runs prefill pods and decode pods as separate pools, sized and parallelized independently, and ships the KV cache between them.

One request through a disaggregated stack

step 1 / 6

The llm-d mechanics, exactly as implemented: decode pods carry the label llm-d.ai/role=decode and a routing-proxy sidecar. The EPP first picks a decode pod, then a decider checks whether the uncached part of the prompt is big enough to justify remote prefill. If yes, it picks a prefill pod and injects the header x-llm-d-prefiller-host-port. The sidecar calls the prefill pod with max_tokens=1 plus kv_transfer_params, and the KV blocks move over NIXL (NVIDIA Inference Transfer Library) — RDMA with GPUDirect, GPU-to-GPU, bypassing the CPU. If the prefiller errors out, the sidecar falls back to local prefill.

When it pays — and when it does not. The llm-d docs are blunt: P/D "is not a target for all workloads". It pays for medium-large models (their example: gpt-oss-120b), long inputs with short outputs (10k in / 1k out — not 200/200), and wide-EP MoE serving. It needs RDMA-class interconnects (the TCP fallback is for testing only). You also tune the pool ratio ("xPyD") and can give each pool different parallelism — the docs' example runs 8 × TP1 prefill pods feeding 2 × TP4 decode pods for a 5k-in / 250-out workload.

v1.0 added the operational half: a DisaggregatedSet CRD (built on LeaderWorkerSet) manages prefill and decode pools as one unit, with revision-aware routing and lockstep rolling updates, so an upgrade does not strand a decode pod on prefillers of the wrong version.

09 · Takeaways

The scaling ladder.

Each rung solves the bottleneck the previous one exposed. Climb only as far as your workload forces you.

  1. One GPU, vLLM defaults. Continuous batching + PagedAttention + automatic prefix caching are free. If the model fits, distributed inference is unnecessary — the vLLM docs say so verbatim.
  2. Model does not fit → tensor parallelism across the GPUs of one node (--tensor-parallel-size). No NVLink? Prefer pipeline parallelism.
  3. Node does not fit → TP × PP: TP = GPUs per node, PP = node count. MoE models scale wider with DP attention + expert parallelism instead.
  4. Need more throughput → replicate (data parallelism). The moment you have replicas, routing quality becomes a first-order performance knob — each replica has its own KV cache.
  5. Replicas → smart routing. llm-d's Endpoint Picker: prefix-cache-aware + load-aware scoring. This is the highest-leverage, lowest-risk llm-d feature — adopt it first.
  6. Long prompts, strict TTFT SLOs → P/D disaggregation, separate pools on RDMA, managed by DisaggregatedSet. Verify the fit: it is not for all workloads.
